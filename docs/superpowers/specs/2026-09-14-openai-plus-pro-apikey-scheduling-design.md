# OpenAI PLUS、PRO 与 API Key 分层调度设计

## 1. 目标

在保留现有定制功能的前提下，先将项目升级到 Sub2API `v0.2.4`，再扩展 OpenAI 高级调度器，实现以下严格回退顺序：

1. 优先使用仍有 5 小时额度的 PLUS 账号。
2. 多个可用 PLUS 账号之间，优先使用 5 小时剩余额度更多的账号。
3. PLUS 池没有可调度账号时，使用 PRO 账号。
4. PRO 账号不受 5 小时额度限制，不读取 5 小时额度参与停调或排序。
5. PLUS、PRO 均没有可调度账号时，使用 OpenAI API Key 账号。
6. Team、Business、Free 和未识别套餐放在 API Key 之后，沿用现有兼容调度。
7. 已建立的粘性会话保持原账号，只有原账号失效时才重新执行完整分层选择。

## 2. 升级基线与范围

升级目标为上游稳定版 `v0.2.4`，而非上游开发分支。升级过程保留当前分支中的商城、支付、API Key 套餐充值、Codex 配置下载、OpenAI 生图路由和 Responses 工具命名空间兼容等定制功能。

当前本地分支相对共同基线包含 43 个定制提交和 107 个改动文件；相对 `v0.2.4`，上游包含约 1473 个新提交。合并预演发现 14 个直接冲突文件，涉及依赖、依赖注入、账号调度、OpenAI 转发、路由和前端接口。升级与调度功能应分阶段验证，以便准确定位回归来源。

## 3. 总体调度流程

```text
previous_response_id / 已有会话粘性账号
                  ↓ 原账号失效
              PLUS 可用池
                  ↓ 无可调度账号
               PRO 可用池
                  ↓ 无可调度账号
             API Key 可用池
                  ↓ 无可调度账号
 Team / Business / Free / 未识别套餐兼容池
```

“无可调度账号”指该池中的候选全部满足至少一种情况：

- 账号被禁用或停调；
- 套餐已过期；
- 不支持当前模型、端点能力或传输方式；
- 账号或目标模型处于冷却期；
- 并发已满且不满足排队条件；
- PLUS 的 5 小时额度达到配置的停调阈值；
- 账号已被加入本次请求的失败排除集合；
- 现有调度器中的代理熔断、收益控制或其他资格检查未通过。

上一级存在可立即获取或允许按现有规则短暂排队的账号时，不进入下一级。

## 4. 套餐识别

在账号领域模型中提供统一、大小写无关、去除首尾空白的套餐分类函数，输入来自 OpenAI OAuth 账号凭据中的 `plan_type`。

| 条件 | 调度层级 |
| --- | --- |
| OpenAI OAuth 且 `plan_type=plus` | PLUS |
| OpenAI OAuth 且 `plan_type=pro` | PRO |
| OpenAI `api_key` 类型 | API Key |
| Team、Business、Free、空值或其他值 | 兼容池 |

Setup Token 等 OAuth-like 类型保持现有协议能力，但除非其套餐能够按上述规则可靠识别，否则进入兼容池。

套餐分类只决定候选池顺序，不跳过上游已有的账号状态、模型能力、传输协议、隐私设置、收益控制、代理熔断和并发检查。

## 5. PLUS 池规则

### 5.1 可用性

PLUS 账号继续使用上游已有的 5 小时、7 天额度快照和账号调度阈值功能。达到任一生效的停调阈值时，由现有机制暂停调度至对应窗口重置。

### 5.2 快照状态

5 小时额度信号分为三种状态：

1. **新鲜且有效**：存在可信的 `codex_5h_used_percent`，窗口未重置，快照未超过现有新鲜度判断。
2. **缺失或过期**：额度值缺失、采集时间缺失、窗口已重置但尚未刷新，或快照超过新鲜度判断。
3. **达到停调阈值**：由现有阈值机制排除，不进入 PLUS 候选池。

缺失或过期时复用现有额度刷新链路触发刷新。刷新完成前，该账号排在同池所有新鲜账号之后；若 PLUS 池全部为缺失或过期状态，这些账号仍保留调度资格，避免账号池空转。

### 5.3 池内顺序

PLUS 候选按以下键依次比较：

1. 新鲜快照优先于缺失或过期快照；
2. 新鲜快照内按 `100 - codex_5h_used_percent` 从高到低；
3. 按账号人工优先级排序，沿用项目中数值越小越优先的语义；
4. 实时负载率从低到高；
5. 排队请求数从少到多；
6. 错误率从低到高；
7. 首字延迟从低到高；
8. 账号 ID 从小到大，保证最终顺序稳定。

额度剩余量是 PLUS 新鲜快照候选中的硬排序键，不与其他评分权重混合，确保“额度更多者优先”的业务规则可预测。

## 6. PRO 池规则

PRO 账号不受 5 小时额度限制：

- 不读取 `codex_5h_used_percent` 判断 PRO 可用性；
- 不因 5 小时快照缺失、过期或显示 100% 而停调、降级或降低分数；
- 不触发仅服务于 PLUS 排序的 5 小时快照刷新；
- 仍保留套餐到期、账号状态、模型能力、冷却、并发和其他通用资格检查。

PRO 池内按以下顺序选择：

1. 账号人工优先级；
2. 实时负载率；
3. 排队请求数；
4. 错误率；
5. 首字延迟；
6. 账号 ID。

## 7. API Key 与兼容池

API Key 池只在 PLUS、PRO 均没有可调度账号时进入。池内继续使用 `v0.2.4` 已有的人工优先级、负载、排队、错误率、首字延迟、倍率、上游成本、模型能力、并发与熔断机制。

Team、Business、Free 和未识别套餐组成末级兼容池，放在 API Key 之后。兼容池不新增套餐专属排序，沿用上游默认调度行为。

## 8. 会话粘性与失败切换

### 8.1 粘性优先

`previous_response_id`、任务所有者绑定和现有会话粘性继续先于套餐分层执行。已经绑定到 PRO、API Key 或兼容账号的会话，即使 PLUS 后续恢复，也保持使用原账号，以保护上下文一致性。

### 8.2 重新选择

当粘性账号因账号禁用、套餐过期、模型不兼容、额度停调、冷却、代理熔断或其他现有硬性条件失效时，放弃本次粘性命中，并从 PLUS 池重新执行完整分层选择。成功回退后，后续请求继续绑定新账号。

### 8.3 同次请求失败

同一次请求内，失败账号加入现有排除集合。重试顺序为：

1. 尝试当前层级中的其他账号；
2. 当前层级候选耗尽后进入下一层级；
3. 已失败账号不在同一次请求内重复选择；
4. 保留上游已有的模型级冷却、账号级冷却和错误分类逻辑。

## 9. 实现边界

主要修改点：

- `backend/internal/service/account.go`：增加标准化套餐分类辅助函数；
- `backend/internal/service/openai_account_scheduler.go`：候选分池、逐级获取、PLUS 硬排序及 PRO 专属排序；
- 对应 OpenAI 调度测试文件：增加分层、额度、粘性和回退测试。

继续复用上游能力：

- Codex 额度采集与快照持久化；
- 定时或按需额度刷新；
- 账号调度阈值和自动恢复；
- Redis 调度缓存；
- 并发令牌与等待计划；
- 代理熔断、模型冷却、账号冷却；
- 现有高级调度配置和可观测指标。

第一版不增加数据库字段，不新增管理员必填项，不通过后台任务频繁改写账号人工优先级。

## 10. 升级实施阶段

### 阶段一：升级到 v0.2.4

1. 从当前 `main` 创建升级分支。
2. 合并 `v0.2.4`。
3. 解决直接冲突，优先采用上游架构，再移植本地业务语义。
4. 重新生成或核对 Ent、Wire 等生成文件，避免手工结果与生成源不一致。
5. 完成后端、前端及当前定制功能回归。

### 阶段二：实现分层调度

1. 增加套餐分类。
2. 在合格候选完成通用过滤后分为 PLUS、PRO、API Key 和兼容池。
3. 为 PLUS 构建额度状态与硬排序键。
4. 为 PRO 构建不含 5 小时额度的排序键。
5. 逐池复用并发获取、排队和失败回退机制。
6. 补充单元测试和集成测试。

### 阶段三：整体回归

1. 后端相关测试；
2. 前端相关测试；
3. 后端与前端编译；
4. 商城、支付、配置下载、生图和 Responses 工具兼容回归；
5. 检查数据库迁移顺序和升级启动过程。

生产镜像更新、容器重启和数据库迁移属于后续发布阶段，在本地升级与验证完成后单独执行。

## 11. 验收标准

自动化测试至少覆盖：

1. 多个 PLUS 时选择 5 小时剩余额度最多者；
2. PLUS 额度相同时按人工优先级和实时负载选择；
3. PLUS 全部达到停调条件后选择 PRO；
4. PRO 的 5 小时字段为 100% 时仍具有调度资格；
5. PRO 的 5 小时快照缺失或过期时排序不受影响；
6. 多个 PRO 按人工优先级、实时负载和排队数选择；
7. PLUS、PRO 均无可调度账号后选择 API Key；
8. API Key 无可调度账号后才进入兼容池；
9. PLUS 快照过期时优先选择快照新鲜账号；
10. 所有 PLUS 快照均过期时仍可选择 PLUS；
11. 已绑定 PRO 的会话在 PLUS 恢复后继续使用 PRO；
12. 粘性账号失效后从 PLUS 重新选择；
13. 当前层级的首个账号失败后优先尝试同层其他账号；
14. 模型不兼容、冷却、并发满和请求排除场景正确逐级回退；
15. 高级调度关闭时保持上游原有行为；
16. 商城、支付、API Key 充值、配置下载、生图和 Responses 工具调用回归通过。

## 12. 可观测性

在现有调度决策日志或指标中增加低基数字段：

- `selected_pool`: `plus`、`pro`、`apikey` 或 `compat`；
- `fallback_from_pool`: 发生跨池回退时记录来源池；
- `plus_quota_snapshot_state`: `fresh`、`stale` 或 `missing`；
- 候选池数量，不记录账号凭据或令牌。

这些信息用于确认实际流量是否遵循 PLUS → PRO → API Key → 兼容池的顺序，并帮助区分额度耗尽、冷却、并发饱和和模型不兼容。
